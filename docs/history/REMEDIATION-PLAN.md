# 跨平台兼容与可靠性整改方案

日期：2026-09-05。审查基线：`2bdd4ef`（标签 `1.38.0.1`）。

状态：方案已整合；本轮已落地 A（测试断言）、B（tar 分流）、E 的静态 fail-closed、F 的 argv/PEN/ps 修复、G 的卸载保护与缓存锁、H 的来源指纹，以及 K 的 ABI 文档首版。C（stty 运行时索引）和 D（SIGILL 归因）仍需真机/新鲜构建证据，不能把本轮代码检查当作已完成的平台验收。本文合并本任务上一轮审查、同事提供的主报告与 QA 核验摘要、`/tmp/report_body.md` 补丁逐文件报告，并对影响修法的关键代码重新核对。临时报告不作为后续构建依赖。

## 1. 目标与总体决策

保留 BusyBox + Cosmopolitan、双架构 APE、full/min 发布包的现有方向。下一阶段的目标是：每一项宣称支持的能力，都能在明确的平台、启动路径和产物上被可信测试验证；每个补丁都能从锁定源码重新应用；失败不能被清理命令、缓存或跳过逻辑隐藏。

采用以下决策：

1. 先修测试判据和构建来源追踪，再用失败用例推动功能修复。测试修复后出现的新 FAIL 如实保留。
2. `stty` 采用 BusyBox 侧运行时索引适配；Cosmopolitan 全局 termios 归一化作为上游设计议题，不作为本轮交付依赖。
3. tar 按压缩能力分流：已启用且支持编码的内置压缩器可自执行；xz 等仅解码的 applet 不能用于创建压缩包，改为调用外部编码器。没有外部编码器时清晰失败，并声明依赖。
4. 公共启动逻辑只维护一份。loader 私有化必须同时修通 launcher、ash 回退和 libc 自 exec 的发现链，不能只移动文件。
5. 当前周期保持锁定工具链和上游版本；功能修复、补丁重组、版本升级分别验收，避免混合归因。

## 2. 合并时修正的关键判断

### 2.1 `stty` 的问题不能仅限定在 macOS/Windows

补丁把 `VINTR=0`、`VERASE=2`、`VEOF=4` 等固定为 Linux 原生 termios 下标。但锁定的 Cosmopolitan 源码 `libc/sysv/consts.sh` 第 926–942 行给出的值如下：

| 逻辑控制项 | BusyBox 当前硬编码 | Cosmopolitan Linux/Windows（运行时逻辑值） | Cosmopolitan macOS |
|---|---:|---:|---:|
| VINTR | 0 | 0 | 8 |
| VERASE | 2 | 2 | 3 |
| VEOF | 4 | 4 | 0 |
| VMIN | 6 | 6 | 16 |
| VTIME | 5 | 5 | 17 |

Cosmopolitan 的 `syscon` 源表为支持合法的零下标，把 Linux/Windows 的零值以 `0+1` 形式编码；上表列的是运行时逻辑下标，不是该生成表的原始表达式。Linux 路径把 ioctl 结果直接写入 Cosmopolitan 的 `struct termios`；Windows `TtyConf.c_cc` 的首槽是 `vline`，后面才是 `vintr`；macOS 的 `COPY_TERMIOS` 原样复制 `c_cc`。这些结构与常量共同说明：不能直接拿 Linux 原生头的下标索引 Cosmopolitan 的 `c_cc`。

因此撤销“Linux 主机正确，标成 Linux-only 即可”的兜底方案。以上是源码机制证据，三平台终端行为仍需回归验证。索引 0 可以合法（例如 macOS VEOF），也可能在某些可选常量中表示不支持，不能用统一的 `index != 0` 判可用。

源码出处均相对于锁定的 Cosmopolitan 提交 `3293fad0a9eac7865c019be98fb993eeb933405e`：`libc/sysv/consts.sh`、`libc/calls/tcgetattr.c`、`libc/calls/termios2host.c`、`libc/calls/termios.internal.h`、`libc/calls/struct/termios.h`、`libc/intrin/nomultics.h`。实施前还须用随当前工具链编译的小探针确认实际常量，排除本地源码与库不一致。

### 2.2 信号与 termios 分别维护约定

信号编号在该快照存在 Linux 归一化路径，不能将这一结论套用到 termios；也不能由“编号正确”推导出 Windows 完整支持该信号。冗余 pin 的删除以当前支持版本的编译和行为测试为依据。死 `SIGEMT` pin 单独清理。

### 2.3 修复 argv 截断不等于无条件加入动态分配

ash 的 loader 回退和 macOS ps 透传确有固定 64 槽数组。实现前须核对全部调用上下文：普通 fork 子进程可动态构造参数，真正的 vfork 子进程不能随意 malloc、修改共享全局或调用复杂初始化。保留主进程预热路径；ps 优先复用现有 argv，仅在需要时复制。loader 参数协议中的 `-` 和原 argv[0] 必须一并验证。

### 2.4 上一轮 `SIGILL` 保留为独立待归因问题

上一轮在本地现有发布 zip 的副本上，macOS 26.6.2 x86_64 的 dd/shuf 出现退出码 132；deep 为 26 PASS/5 FAIL，完整冒烟为 169 PASS/3 FAIL/1 SKIP/5 SOFT。网络项同时出现沙箱 `bind: Operation not permitted`。

这些结果既不能直接归因为 macOS 26 回归，也不能按环境差异全部忽略：本地 `work/` 有未纳入补丁的 `APE_EXEC_DEBUG`，`dist/` 又未纳入版本控制。先固定产物 SHA256、重建来源、CPU、OS、运行格式和沙箱条件，再定位崩溃点。前述 PASS 数仅为旧测试输出，不作为新基线。

## 4. 各工作包的实施与验收

### A. 让测试能可靠地失败

范围：`tests/smoke-full.sh`、`tests/deep-test.sh`、`tests/smoke.sh`，新增必要的测试辅助程序。

- 每项独立工作目录；用 trap 清理，保留断言返回码、stdout、stderr、执行命令和实际运行产物。不机械依赖 `set -e`，也不把管道末端成功视为整条数据生产链成功。
- 修复 `; rm` 吞失败、`|| echo` 假成功、`test $? -ge 0`、无条件 `true`、telnet 的 `tn` 首参错误、未真正 zip/unzip 的用例。
- 断言输出精确值或内容，校验文件确实生成、长度正确。cpio 解包使用空目录；`wc -m` 校验预期字符数；SHA 用固定非空向量和系统工具作独立对照，不能仅比对被测实现的两次结果。
- 对内置 applet 测试限制 PATH，防止 BusyBox 执行失败后悄悄使用宿主工具；需要外部 xz 的测试显式提供单独 PATH，记录所用编码器。
- SKIP 仅对应明确的配置/平台缺项。预期不支持的行为应测试其错误结果；已知缺陷按用例 ID 记录预期失败，不能整组忽略。缺 PTY、网络权限等属于基础设施条件不足，不能记为功能 PASS。

验收：人为将断言改错、让生产者失败但下游输出合法、使清理成功、移除被测 applet，均须使相应测试或支持清单校验失败。完整报告中的每个 PASS 必须有实际断言；失败日志可定位到具体命令。

### B. 修复 tar 创建 xz 压缩包

范围：BusyBox `archival/tar.c` 的权威补丁及归档回归。

- 以实际编译配置和编码能力选择 gzip/bzip2 等内置 applet，不能只按名字存在判断支持压缩。
- xz，以及实际入口可选择的其他仅解码格式，使用外部可执行编码器，绕开 PREFER_APPLETS 的错误路由。PATH 恰好指向 BusyBox 的 xz 别名时也必须失败可诊断。
- 复核 `xvfork()` 后靠共享 `vfork_exec_errno` 传错的逻辑。按平台可用语义设计 exec 错误通道，并检查压缩子进程的完成状态，覆盖“exec 成功、编码中途失败”的情况；不接受只改 exec 目标。
- 缺编码器时返回非零并说明依赖，不把空或截断文件标成成功；不主动删除用户原有目标文件。

验收：无外部 gzip/bzip2 时 `tar czf/cjf` 往返成功；提供外部 xz 时 `tar cJf` 与独立工具交叉验证；缺 xz、假编码器中途失败、空归档、标准输出归档、路径带空格均有准确结果。tar 的父进程不得因输入为空而漏报子进程失败。

### C. 修复 stty 的运行时布局适配

范围：BusyBox `coreutils/stty.c` 的权威补丁、兼容头、TTY 测试。

- 删除 V* 的 Linux 原生数值 pin。以稳定的内部控制项 ID 保存静态信息，在运行时从工具链取得实际下标；可采用运行时构造表或索引解析函数，避免全局可变表破坏 NOEXEC 重入。
- 将依赖 V* 值的 `#if` 比较改成运行时逻辑；名称表、枚举、控制表来自同一描述。分开处理可选项是否支持、合法的 0 下标、禁用字符值、VMIN/VTIME 与 VEOF/VEOL 的关系。
- Linux/macOS 在专用 PTY 上由独立观察程序读取设置结果，并做反向验证；Windows 用独立 console/ConPTY 测试，区分进程内 tty 模拟状态与可跨进程观察的系统状态。
- 读、写、`sane`、raw/canonical 往返和恢复都纳入验证；避免修改用户正在使用的终端。上游归一化提案须评估 ABI 影响，短期修复不等待它。

验收：intr/erase/kill/eof/start/stop/min/time 的读取与写入符合各平台实际语义；更改一个控制项不污染其他槽位；无 tty 时准确报错。真机环境不足的项标为未验证，不对该路径作完整支持声明。

### D. 完成 SIGILL 归因

先记录旧产物与新鲜构建产物的 SHA256，用 dd 的最小复制和 shuf 的固定输入分别复现。对比 launcher 原生缓存、loader、单架构与 fat 形态，记录工具链 manifest、CPU 特性及崩溃指令/调用栈。

受限环境与正常运行环境分别验证；允许的诊断条件下排除环境因素后，再决定修 BusyBox、libc、指令选择还是产物生成。旧产物来源不一致时保留记录，不把它直接当作新提交缺陷。

验收：有可重复用例和证据支持的根因或明确的环境限制；若新鲜构建在承诺平台仍 SIGILL，该平台发布必须受阻，不能改成 SOFT 隐藏。修复后校验复制字节数/内容和 shuffle 输入输出集合，而非仅检查程序退出。

### E. 补齐 64K 全链路门禁

范围：`scripts/check-ape-64k.sh`、`tests/qemu-64k-test.sh`、CI。

- 静态检查同时识别 loader 与实际载荷，验证架构、文件范围、程序头数量、段范围、对齐和最终文件偏移的 64K 同余；检查 MODERN e_flags，覆盖既往两类链接回归。
- 缺 readelf、解析器异常、缺期望 loader/载荷、零 LOAD 段、截断文件全部非零退出。可用结构化解析减少对 readelf 文本格式的依赖，检查结果输出明确的对象与失败原因。
- 临时文件使用唯一目录和 trap，避免并发检查同样长度产物时撞名。工具链 verify 的 `bad` 必须传播为整个验证失败。
- QEMU 直接用 `sysconf(_SC_PAGESIZE)`/等效实际值断言 65536，不用内存大小推算。来宾逐项断言成功，宿主等待完成标记并设置超时；缺标记、来宾失败或超时使任务失败。
- 嵌套测试必须重新执行被测 APE，不以独立 ELF 代替。实现 `--full` 实际执行套件；先接入手动/定期工作流，发布候选至少运行一次。可用内核的 binfmt 路径另测。

验收：保留或构造 16K loader、0x4000 载荷偏移、错误 e_flags、缺架构等坏样本，逐个被拒绝；正确的单架构/fat 在 4K 与 64K 来宾通过。16K 真机覆盖单独标记状态，不由 4K/64K 成绩代替。

### F. 修复配置和 exec/ABI 边界

- `bb_argv0` 仅保留一处定义，移出 NUM_SCRIPTS 和单/多 applet 分支；测试嵌入脚本开/关及受支持的单 applet 配置。
- ash 完整保留所有参数；核对 loader `- PROG ARGV0 ...` 协议，在合法上下文中分配/释放，分配失败准确报错。mac ps 透传不静默裁参数。
- PEN 参数解析在访问 `f+1/f+2` 前检查实际边界，处理空串、超长填充、缓冲截断和未终止字符串；不把 loader 当作 BusyBox 自身执行。
- ps 从真实头文件取得 `tprecode16to8` 原型，去掉返回 `void *` 的手写声明；用工具链平台判定接口替代 `__hostos` 魔数。集中记录仍需引用的私有接口。

验收：0/1/63/64/65/256 参数，空参数、中文、空格、反斜杠和引号逐字节往返一致；Unix 测换行参数。嵌套 exec、变更当前目录、冷启动和缓存复用均保持自身路径正确；参数长度上限以 OS 错误明确返回。

### G. 统一安装与启动链路

- 先修 `--prefix` 缺参、路径规范化、危险目录拒绝与安装 manifest；卸载只清理本项目登记的文件，保留其他文件。`--win-only` 实际按选项工作，缺资产时报错，不生成占位空 ELF。
- `install.sh` 安装同一份 launcher 或从同一源生成，不再维护独立 heredoc 实现。Windows 识别使用 mingw*/msys*/cygwin*，未知架构明确失败。
- 缓存键覆盖主产物、loader/assimilate、启动策略版本与 OS/架构；采用内容摘要、独立临时文件、原子 rename、目录权限与锁。不要求 macOS 未必预装的外部 flock，可采用可移植锁目录并处理超时/陈旧锁。
- loader 迁移至项目私有目录时同时更新所有查找者，保留识别要求或替换识别机制；验收前不移除现有有效路径。缓存转化失败不能留下半成品供下一次运行。
- 合并三处 binfmt 注册逻辑，核验现有规则是否启用、flags 与解释器是否匹配；识别其他安装者的 loader，不直接覆盖。持久化与卸载范围在安装记录中明确。

验收：安装与零安装的 full/min 运行结果一致；冷缓存并发 20 次、热缓存、残留临时文件、只读发行目录、损坏缓存、路径带空格/中文/引号、无可写缓存都得到一致成功或准确错误；母本摘要不变，危险 prefix 测试不得触及真实危险目录。

### H. 保证改补丁后确实构建了新代码

- `.bb-patch-ok`、`.bb-restore-ok`、`.bb-cosmo-prepared` 不能仅凭存在跳过；记录源码、补丁顺序、内容、配置和驱动版本指纹。工具链目标存在也不能直接跳过 make 的依赖判断。
- 优先以指纹建立新的独立构建目录，保留旧工作树供差异分析；应用补丁失败即停止，取消“可能已含或版本不符，跳过”的成功路径。
- 源码缓存以锁定归档和受控提取目录为准；现有目录不能自动标记为已校验。统一 `sha256sum`/`shasum -a 256`；下载先写临时文件，校验后落盘。
- 工具链 build 的正式模式执行 assemble 后的自包含 verify；缓存恢复也验证 manifest 和关键能力。旧 `/tmp` 参考工具链比对保留为可选诊断，不作为新机器前置。
- manifest 记录材料、补丁摘要、生成配置、编译选项、头/库/crt/apelink/loader 来源与摘要。入口可执行不等于定制工具链有效；官方未打补丁的下载模式不能通过正式发布门禁。

验收：修改任意补丁后构建必定更新或拒绝复用；干净目录中不依赖历史 `/tmp` 树即可重建与验证；故意替换旧 apelink、loader 或不匹配的库会失败。本地调试残留与权威补丁生成树的差异必须被报告。

### I. 统一发布内容和支持声明

- 增加一份机器可读能力清单，维度包括 OS、CPU、OS/内核版本、页大小、启动路径、包类型、权限与功能；区分支持、已知限制、待验证、仿真。生成当前状态说明，历史验证记录保持历史身份。
- 修正 macOS ARM64“已修复”与“待真机”的冲突，重新验证 Linux 无 binfmt 路径；Windows ARM64 明确为 x86_64 仿真路径。
- full 包包含 KNOWN-LIMITATIONS、安装说明、NOTICE、对应许可文本与源码获取/重建材料；min 所引用的说明必须可实际获得。纠正 NOTICE 中 busybox-w32“仅参考、不入产物”与 make/pdpmake 移植的冲突，按真实代码来源核对归属。
- BUILD_DATE 使用 SOURCE_DATE_EPOCH，归一化时间、排序、权限、zip 元数据和路径。先创建全新临时 zip 再原子替换，防止更新旧 zip 时残留已删除文件。
- 使用 SHA256SUMS，排除清单自身；验证解压后每项摘要。发布源码包对应同一提交与补丁序列；签名/来源证明作为后续发布机制接入项。

验收：相同输入与 epoch 在两个干净目录生成一致产物；对完整 zip 声明逐位可复现前必须实际比对 zip。full/min 文件清单、说明与测试对象相符，发布说明不含本机绝对路径，旧包多余成员不能混入新包。

### J. 将能力矩阵落实到 CI

- 每次提交：脚本语法及合适的静态检查、测试框架负向验证、补丁来源校验、工具链验证、双架构构建、坏样本检查、各稳定平台发布包测试。
- 正式测试使用归档解压后的产物，校验摘要。至少覆盖 full/min、零安装/安装后、冷/热缓存；Linux 区分 ELF、无 binfmt loader 与注册 binfmt。min 测试从空的测试用户目录启动，不手工预置 loader 掩盖安装问题；通过独立用户/容器或测试入口完成隔离。
- macOS 覆盖既有系统与可用的新系统 runner；macOS ARM64 先修测试，再建立可比基线后提升为发布门禁。Windows ARM64 保留仿真标识。
- 服务端按启用能力测试 httpd/ftpd/inetd/ssl_server：回环请求、真实响应、fork/exec 后 socket 存活、退出与清理、超时和端口隔离。先收集每个用例的证据，不把所有失败预归因 #1174；未启用的 applet 记录为能力缺项。
- TTY、QuickEdit/交互、hush、IPv6、信号异值、非空及多块散列向量分专项加入。已有 smoke 外网项目改成本地夹具或单独网络测试，保持默认矩阵可离线执行。
- 按用例 ID/平台维护允许的 SKIP/SOFT/预期失败及原因，新增项或结果变化需要显式更新；不能仅设置一个宽松的总数量上限。

验收：失败保留日志和产物摘要；基础设施缺口与产品失败可区分；所有发布声明可追到对应测试结果。同一被测代码不能既生成答案又充当唯一裁判。

### K. 补丁治理与上游贡献

- 新增 `docs/COSMO-ABI-CONTRACTS.md`，按下节模板记录每个依赖；范围包括已知安全的归一化规则及尚未承诺稳定的私有接口。
- 短期保留 full→restore 的顺序但将整条序列作为不可分割的构建输入；中期改为有明确 `series` 顺序的主题补丁，或由主题补丁确定性生成聚合补丁。选择一个权威来源，避免巨型补丁和快照双重手改。
- 移除补丁中的生成 usage.h，验证标准生成规则仍完整；master-snapshot 废弃或明确由权威序列生成并自动校验。清理死 pin 和调试残留时逐项核对，保留有价值诊断为受控功能。
- applet 清单区分真实实现和 stub；config、kbuild、stub 与别名生成/检查保持一致，防止“help 中存在但永远失败”被当成支持。
- 分别准备 mkntcmdline、PEN、apeflags、64K 的最小上游补丁、复现和测试，termios 提设计说明。提交上游前核验最新源码和既有 issue，防止重复修复；外部 issue/PR 提交是独立的后续动作。
- 在独立构建目录演练下一目标 BusyBox/Cosmopolitan 版本，先确认版本可获取。记录补丁自然消融、冲突和行为变化，不因“干净 apply”即认为兼容。

### L. 后续形态与性能演进

保留 APE 的便携价值，按明确场景评估原生 Linux ELF 作为快捷路径，binfmt 作为管理员可选部署。macOS 原生 Mach-O 和 Windows 原生 ARM64 属于新构建路线，单独评估，不承诺当前工具链可直接产出。fork 优化以真实基准和错误路径测试为前提，不为性能重新引入未经证明的共享状态假设。

## 5. ABI 约定文档的必需内容

每个条目记录：约定 ID、锁定上游提交及源码符号、调用位置、成立的平台/模式、失败表现、验证用例、升级检查方式。下表作为首版清单，不把当前私有实现描述成稳定公共 ABI。

| 约定 | 需要记录/验证的内容 | 对应工作包 |
|---|---|---|
| TERMIOS-CC | per-host 索引、Linux/NT 的 vline 首槽、合法零索引、可选项 | C |
| SIGNAL-NUMBER | Linux 编号归一化边界与各主机实际支持的信号 | F/J |
| APE-ARGV | `- PROG ARGV0 ...`、MODERN e_flags、argv 字节往返 | E/F |
| SELF-PATH | GetProgramExecutableName、KERN_PROCARGS2 布局、预热与边界 | F |
| LOADER-DISCOVERY | OldApeLoader 名字/路径规则，launcher/ash/libc 一致发现 | G |
| FORK-ERROR | fork/vfork 调用上下文、错误通道、子进程完成状态 | B/F/J |
| WINDOWS-ABI | NT 头、真实转码原型、平台判定、模拟 tty/socket 能力 | F/J |
| PAGE-LAYOUT | 内嵌 loader、载荷最终偏移、PT_LOAD、4K/16K/64K | E |
| TOOLCHAIN-SET | 头/库/crt/linker/loader 同源与补丁指纹 | H |
| APPLET-CAPABILITY | 编码/解码区别、stub、外部工具依赖及配置组合 | B/I/K |

## 6. 实施批次与发布门槛

建议按以下批次提交。每批功能修复与对应回归测试一起审阅，使用新的构建目录，避免历史调试树污染验证。

| 批次 | 交付 | 依赖与通过条件 |
|---|---|---|
| 1 | A + H 的最小来源/缓存修复 + G 的 prefix/卸载保护 | 负向测试能失败，补丁变更不会复用旧树，危险路径被拒绝 |
| 2 | B + F 的 bb_argv0 修复 | 归档正/负场景正确，关闭嵌入脚本可构建 |
| 3 | C + D | 三平台 termios 验证；SIGILL 根因或限制有可复查证据 |
| 4 | F 剩余项 + E 静态门禁 | 长参数/路径/ABI 边界通过，历史坏 APE 样本被拒绝 |
| 5 | G 剩余项 + H 完整工具链验证 | 安装与零安装行为一致，并发、升级、缓存失败路径可靠 |
| 6 | E 的 QEMU + I + J 的发布矩阵 | 对确切发布归档验证，状态说明准确，发布材料齐全 |
| 7 | K + L | 补丁治理、上游准备和下一版本演练；不拖住已验修复 |

一次稳定化发布的完成条件：

- 所有 P0 已修复，或对无法支持的能力有明确运行时拒绝和发布声明；不能以陈旧的全绿记录代替验证。
- 关键 P1 的配置、长参数、安装、缓存、工具链来源均已验收，强制矩阵没有未知 FAIL 或新增未解释的跳过。
- full/min 的实际归档通过对应平台/启动路径测试；64K 正式声明有本候选产物的静态与 QEMU 证据。
- 构建从锁定材料完成，源码、补丁、工具链和归档摘要可追踪；源码包、说明和许可材料对应同一版本。
- 发布报告区分已实测、代码机制证实、待真机验证和明确不支持，不使用“全功能”概括仍有边界的路径。
